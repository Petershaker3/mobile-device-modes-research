# وثيقة خط الأساس ومتطلبات المنتج

> **هذه الوثيقة هي نقطة المرجع الوظيفية والمعمارية للمشروع.** ملفات المجالات ومراجعات الأدوات تحتفظ بالأدلة والتفاصيل. عند التعارض، لا نحذف التاريخ: نحدّث القرار هنا ونضع رابطاً إلى المراجعة التي تشرح سبب القرار.

**المستودع:** `Petershaker3/mobile-device-modes-research`  
**الحالة:** بحث وتحليل وتصميم متطلبات؛ لا يوجد تطبيق منتج منفذ أو تكاملات تم اعتمادها واختبارها على أجهزة فعلية حتى تاريخ هذه المراجعة.  
**آخر تجميع تنظيمي:** 12 نوفمبر 2026.

## 1. تعريف المنتج

برنامج Windows لإدارة أجهزة Android وأدواتها من واجهة واحدة، يركز على:

1. اكتشاف الهاتف وطرق اتصاله وقراءة المعلومات المتاحة بأمان.
2. البحث عن التطبيقات وتحميلها من مصادر متعددة، ثم فحصها وتثبيتها بأوسع تغطية عملية للصيغ.
3. إدارة التطبيقات المثبتة عبر USB وWireless ADB، مع البحث والتصفية والتصدير.
4. إعدادات DNS وحجب الإعلانات وفق الإمكانات الفعلية لإصدار Android.
5. تشخيص تعريفات Windows المرتبطة باتصال Android وإصلاحها بحذر.
6. إتاحة خدمات البرنامج لوكلاء الذكاء الاصطناعي، خصوصاً Codex، عبر MCP بصلاحيات محكومة.

**المنتج ليس** أداة تفليش عامة أو أداة تجاوز حماية أو منصة لإزالة الحسابات. قراءة أوضاع Qualcomm وMediaTek وبروتوكولاتها خارج النطاق الحالي، كما أن مقارنة التراخيص ليست ضمن البحث.

## 2. القرارات المعتمدة التي يجب ألا تضيع بين ملفات البحث

| القرار | القاعدة المعتمدة |
|---|---|
| الأولوية الوظيفية | تثبيت التطبيقات بأكبر تنوع عملي من الصيغ والحالات هو الأولوية الأولى لمحور التطبيقات. |
| إعادة الاستخدام | نبحث عن مشاريع GitHub والأدوات الجاهزة ونراجع مصدرها قبل كتابة بديل؛ لا نخترع العجلة. |
| التحليل العميق | تحليل ELF وDT_NEEDED وSONAME والرموز تشخيص متقدم مؤجل، وليس شرطاً لمسار التثبيت V1. |
| محرك التثبيت | محرك موحد يوجّه كل صيغة إلى Adapter متخصص؛ لا يوجد Generic Extractor يفترض أن كل الأرشيفات متشابهة. |
| مصدر التطبيق | APKPure وF-Droid وAPKMirror مصادر ضمن نطاق المنتج، ولكل مصدر Provider Adapter وسياسة مستقلة. |
| F-Droid | أولوية التكامل الأصلي بسبب الفهارس الموقعة وبيانات الإصدارات وإمكانية التحقق من سلامة الملفات. |
| APKPure وAPKMirror | لا نفترض API عامة مستقرة. نستخدم تدفقات الموقع الطبيعية فقط، ولا نتجاوز CAPTCHA أو Cloudflare أو حدود الوصول. |
| واجهة وMCP | كلاهما يستدعيان Service Layer نفسها؛ لا يعيد MCP تنفيذ منطق الأعمال. |
| الأمان | Read-only افتراضياً. كل تغيير مؤثر يمر بـPreview ثم Approval ثم Apply ثم Verify. |
| استهداف الجهاز | كل عملية هاتف مرتبطة بـSerial/Device ID صريح؛ لا نختار أول جهاز تلقائياً. |
| التعريفات | التشخيص قبل الإصلاح، ومصادر Microsoft/Google/OEM الرسمية، مع تحقق وتراجع. |
| حدود البحث | لا اختبار فعلي ولا اعتماد دمج لمجرد وجود README أو CI أو ميزة معلنة. |

## 3. ترتيب الأولويات الموحد

### P0 — أساس المنتج ومحرك تثبيت التطبيقات (حد V1 الأساسي)

P0 هو الحد الأدنى المطلوب لاعتماد أول نسخة قابلة للاستخدام في مسار التثبيت. لا يعني أن كل وظائف المنتج أو كل الصيغ يجب أن تدخل الإصدار الأول. العناصر المصنفة P1 توسعة تالية بعد ثبات P0، وP2 مراحل لاحقة. الصيغ المشفرة أو مجهولة البنية تظل غير مدعومة إلى أن تُراجع وتُختبر بصورة مستقلة.


- اكتشاف أجهزة Android المتصلة عبر USB وWireless ADB، مع تمييز offline وunauthorized.
- جلب DeviceSpec الضروري: Android API level، ABI list، density، locales عند توفرها.
- تحليل APK المفرد وManifest والـpackage/version/minSdk والتوقيع.
- دعم base + split APKs والتحقق من اكتمال المجموعة وتطابق package/version/signing certificates.
- دعم APKS عبر Google bundletool واختيار splits المطابقة للجهاز.
- إدارة تنزيل آمن وملفات staging وprogress وcancellation وrecovery.
- تثبيت موجّه إلى جهاز واحد والتحقق بعد التثبيت من package/version؛ لا نخلط نجاح أمر ADB مع تحقق وجود التطبيق.
- رسائل فشل واضحة وقابلة للتشخيص، ومصفوفة اختبارات تشمل الملفات التالفة والتوقيع والـABI والانقطاع وتعدد الأجهزة.

**ترتيب الصيغ الحالي:**

| الأولوية | الصيغة | المسار |
|---|---|---|
| P0 | APK | فحص ثم `adb install` |
| P0 | Base + Split APKs | تحقق المجموعة ثم `adb install-multiple` |
| P0 | APKS | Google bundletool وDeviceSpec |
| P1 | APKM غير المشفر | Parser/Adapter خاص بالبنية المكتشفة |
| P1 | XAPK | Parser/Adapter؛ وOBB مرحلة منفصلة |
| P2 | AAB | تحويل اختياري عبر bundletool؛ ليس APK جاهزاً |
| مؤجل | APKV المشفر وAPKM legacy المشفر | لا دعم قبل إثبات الحاجة ووجود عينات واختبارات مناسبة |

### P1 — اكتشاف التطبيقات من المصادر وتنزيلها

- البحث في F-Droid وAPKPure وAPKMirror من شاشة موحدة.
- عرض المصدر بوضوح، Package ID، المطور، الإصدار، variant، الحجم والتاريخ عند توفرها.
- اختيار الإصدار والـvariant يدوياً مع إظهار التوافق أو المعلومات المجهولة.
- تنزيل إلى staging مع التحقق من TLS والـredirects وحدود الحجم والوقت.
- F-Droid: التحقق من توقيع الفهرس بمفتاح موثوق، ثم مطابقة hash للملف.
- APKPure/APKMirror: لا API مفترضة ولا scraping هش أو تجاوز لحماية الموقع.
- بعد التنزيل: SHA-256 عند توفره، فحص الأرشيف، التوقيع، Package ID، Device Compatibility.
- التنزيل لا يعني تثبيتاً تلقائياً؛ التثبيت خطوة منفصلة بموافقة المستخدم.

### P1 — إدارة التطبيقات

- قائمة التطبيقات System/User وEnabled/Disabled.
- بحث بالاسم وPackage ID، وفلاتر حالة التطبيق والمصدر وتاريخ التثبيت والتحديث وABI عند توفر البيانات.
- تفاصيل package/version/installer/UID/path والحقول المتاحة فعلياً.
- Install/Uninstall/Enable/Disable/Restore، مع تحذيرات منفصلة لتطبيقات النظام.
- تصدير APK أو Split APKs دون الادعاء بأن ذلك ينسخ بيانات التطبيق الخاصة.
- عمليات Batch بنتيجة مستقلة لكل تطبيق وسجل عمليات منقح.

### P1 — اتصال وقراءة معلومات الجهاز

- اكتشاف USB interfaces وVID/PID وHardware IDs وCOM ports، مع إعادة الاكتشاف بعد تبديل الوضع.
- ADB وFastboot وFastbootd وMTP/WPD.
- مسارات Samsung MTP/AT وDownload Mode/Odin، وXiaomi Mi Assistant، وHuawei/Honor Fastboot، وفق حدود الدليل لكل موديل.
- مصفوفة قدرات وانتقالات حسب الموديل، لا ادعاء دعم عام لكل شركة.
- كل حقل Read Info يحمل مصدره وحالة الدليل: Success / Unsupported / PermissionDenied / NotReported / Timeout / DeviceDisconnected / MalformedResponse.
- جمع IMEI أو أي معرف حساس ليس افتراضياً؛ يجب تبرير الحاجة وإخفاؤه في السجلات والتقارير.

### P2 — DNS وإعدادات الشبكة

- التمييز بين Android Private DNS (DoT hostname)، وDNS التقليدي لكل شبكة، وتطبيقات Local VPN.
- قراءة الحالة أولاً، ثم Preview للتغيير، موافقة منفصلة، تطبيق، ثم قراءة/اختبار/استعادة.
- لا نفترض وجود أمر ADB عام يضبط DNS لكل شبكات Wi-Fi على كل إصدارات Android.
- عرض تعارض VPN وPrivate DNS، وعدم ادعاء نجاح حجب الإعلانات بمجرد تغيير قيمة إعداد.

### P2 — تشخيص تعريفات Windows

- قراءة PnP/SetupAPI/Configuration Manager وHardware IDs وحالة الواجهة والتعريف.
- اقتراح Microsoft/Google/OEM source المطابق فقط.
- لا تثبيت أو إزالة أو استبدال تلقائي؛ Preview وموافقة منفصلة.
- حفظ حالة قبل/بعد، وإتاحة Rollback حيث يدعمه Windows.
- التحقق من ADB وFastboot وMTP كلٌ على حدة بعد الإصلاح.

### P2 — MCP / تكامل AI

- خادم محلي، STDIO كبداية.
- أدوات القراءة Read-only افتراضياً.
- أدوات التغيير منفصلة وتفرض الموافقة داخل الخادم نفسه، لا بالاعتماد على واجهة Codex فقط.
- لا Shell عام افتراضياً، ولا Administrator مفتوح، ولا اختيار تلقائي لأول جهاز.
- الأدوات تستخدم نفس Services وtyped results التي تستخدمها GUI.
- اختبار الربط مع Codex فعلياً شرط لاعتماد التكامل.

## 4. المعمارية المنطقية الموحدة

```text
Windows Desktop UI                 AI Client (Codex)
        |                                  |
        |                           MCP Server (local)
        |                                  |
        +-----------> Application Services <+
                        |
     +------------------+-------------------------+
     |                  |                         |
 Device Services   App & Install Services    Driver Services
     |                  |                         |
 USB / ADB         Source Providers           Windows PnP APIs
 Fastboot / WPD    Download Manager           Official Driver Sources
 Vendor Adapters   Format Adapters             Repair / Verify
     |                  |                         |
     +------------------+-------------------------+
                        |
                 Shared Policy Layer
       Device Targeting / Approval / Audit / Recovery
                        |
                Android Device / Windows
```

**مبادئ الفصل:**
- Provider Adapter مسؤول عن اكتشاف التطبيق/الإصدار وحل رابط التنزيل؛ لا يثبت التطبيق.
- Format Adapter مسؤول عن تحليل صيغة الملف وإنتاج Install Plan؛ لا يقرر جهازاً من تلقاء نفسه.
- Device Adapter مسؤول عن الاتصال وتنفيذ عملية محددة على Serial معلوم.
- Application Service Layer تنسق المراحل وتفرض السياسات وتنتج نتيجة موحدة.
- GUI وMCP لا يتصلان مباشرة بأوامر shell أو تفاصيل parser.

## 5. مسار تثبيت التطبيق من البداية للنهاية

1. **Search:** البحث عن التطبيق في المصادر المحددة.
2. **Version & Variant Selection:** اختيار إصدار وvariant واضحين.
3. **Download Preview:** عرض المصدر والرابط النهائي والحجم والـhash المتوقع إن توفر.
4. **Download:** تنزيل متدرج إلى staging مع cancellation وإدارة partial files.
5. **Format Detection:** تحديد الصيغة من المحتوى والبنية، وليس الامتداد وحده.
6. **Package Inspection:** قراءة manifest والهوية والإصدار والحد الأدنى للنظام والتوقيع.
7. **Secure Extraction:** استخراج محدود وآمن عند الحاجة، بأسماء staging مولدة وحدود موارد.
8. **Device Matching:** مطابقة ABI/SDK/density/locale واختيار splits المطلوبة.
9. **Install Preview:** عرض الجهاز المستهدف والملفات والآثار والخيارات.
10. **Approval & Install:** موافقة مستقلة، ثم تنفيذ عبر install أو install-multiple أو bundletool.
11. **Verification:** إعادة قراءة package/version؛ وتبقى launch verification مرحلة اختيارية منفصلة.
12. **Reconciliation & Audit:** تسجيل النتيجة، إعادة قراءة حالة الجهاز والحزمة بعد timeout/disconnect، وتحديد ما إذا كانت العملية اكتملت أو فشلت أو بقيت حالتها غير محسومة؛ ثم تنظيف الملفات والجلسات المؤقتة بأمان. لا نفترض إمكانية Rollback لكل عملية، ولا نعرضها كقابلة للعكس إلا إذا كان ذلك مدعوماً ومختبراً للمسار المحدد.

لا يجوز القفز من Download إلى Install، ولا من ADB exit code إلى إعلان نجاح نهائي.

## 6. ضوابط الأمان المشتركة

- لا تثق في اسم الملف أو امتداده أو metadata التي يرسلها مصدر خارجي.
- HTTPS/TLS، redirects محدودة، ومنع SSRF والوصول إلى localhost/private network عبر روابط التنزيل.
- منع ZIP Slip وZip Bomb والروابط الرمزية وتضارب أسماء الملفات؛ حدود على عدد الملفات والحجم المضغوط والمفكوك والوقت والذاكرة والمساحة.
- Streaming للملفات الكبيرة، لا read-all إلى الذاكرة.
- تحقق APK signing certificate؛ hash يثبت تطابق bytes فقط ولا يثبت هوية الناشر.
- لا تعبر cookies أو tokens بين المصادر، ولا تسجل بيانات جلسات أو IMEI أو Serial دون ضرورة.
- لا downgrade أو test-only أو grant permissions تلقائياً.
- لا تنفيذ أوامر Shell عامة عبر MCP.
- لا إصلاح تعريفات أو تغيير DNS دون معاينة وموافقة وتحقق.

## 7. حالة الأدلة والتنفيذ

| المجال | ما هو موجود الآن | ما لا يزال غير مثبت |
|---|---|---|
| أوضاع الاتصال وRead Info | بحث ومراجع ومصفوفات adapters وانتقالات | توافق عملي حسب الموديل واختبارات الأجهزة |
| أدوات جاهزة | مراجعات README/source/Community لبعض المرشحين | اعتماد نسخة ودمجها واختبارها على Windows |
| APK/APKS/APKM/XAPK/OBB | متطلبات ومحرك موحد وتدقيق parsers/installers | تنفيذ adapters وcorpus واختبار حقيقي على الأجهزة |
| مصادر التنزيل | تصميم F-Droid/APKPure/APKMirror ومحددات الثقة | إثبات تدفقات التنزيل المباشرة واختبار كل مصدر runtime |
| إدارة التطبيقات | متطلبات ADB ومرشحو أدوات وفلاتر | اختبارات USB/Wireless متعددة الأجهزة |
| DNS | تصميم ومسارات وقيود واختبارات | تنفيذ واختبار على Android مستهدف |
| تعريفات Windows | تصميم تشخيص وإصلاح آمن ومصادر | Hardware-ID matrix واختبارات إصلاح/تراجع |
| MCP | معمارية ومراجعة خوادم مرشحة وسياسات أمان | بناء الخادم وربطه بـCodex واختبار كل أداة |

**قاعدة الحالة:** موثق نظرياً ≠ موجود في الكود ≠ معلن من المطور ≠ CI ناجح ≠ اختبار Runtime ≠ اختبار Hardware. يجب تسمية نوع الدليل دائماً.

## 9. قرارات بيئة التشغيل المفتوحة قبل التنفيذ

هذه نقاط لم يُحسم لها اختيار نهائي بعد. لا يجوز تحويلها إلى افتراضات داخل الكود أو وصف المنتج:

| القرار المفتوح | ما يجب تحديده | أثره |
|---|---|---|
| إصدارات Windows | أقل إصدار مدعوم، وإصدارات Windows التي ستدخل الاختبار | اختيار واجهة التطبيق وواجهات النظام وحزم التوزيع |
| معمارية Windows | x64 فقط في البداية أم دعم ARM64 أيضاً | اختيار الحزم والاعتماديات وبناء CI |
| إصدارات Android | أقل API level مستهدف، ومصفوفة الإصدارات التي ستختبر | تحديد توفر Wireless Debugging وPrivate DNS وسلوك Package Manager |
| أدوات التشغيل | طريقة توفير ADB Platform Tools وJava/bundletool عند الحاجة | التثبيت والتحديث والتحقق من سلامة الاعتماديات |
| سياسة الإصدارات | تثبيت نسخ الأدوات ومواعيد تحديثها وآلية الرجوع | قابلية إعادة البناء وتجنب تغير السلوك دون مراجعة |
| حدود العمليات | مهلات كل عملية، وحدود الملفات والذاكرة والمساحة، وسلوك الإلغاء | حماية البرنامج من التعليق أو استهلاك الموارد |
| فشل العمليات الجزئية | حالات timeout/disconnect أثناء install-multiple أو OBB أو cleanup | تصميم reconciliation وإعادة المحاولة ومنع الإبلاغ الكاذب عن النجاح |
| الاحتفاظ بالسجلات | مدة الاحتفاظ ومكان التخزين وحقول التنقيح | الخصوصية والتشخيص واستعادة سجل العملية |

**قاعدة التعامل مع الفشل:** كل عملية طويلة أو متعددة الخطوات يجب أن تمتلك Operation ID وحالات صريحة مثل Pending وRunning وSucceeded وFailed وCancelled وOutcomeUnknown وNeedsReconciliation. لا تُعاد العملية تلقائياً إذا كان من الممكن أن تكون قد نُفذت جزئياً؛ افحص الحالة أولاً. يجب أن تكون عمليات التنظيف محدودة ومحمية من حذف ملفات لا تخص العملية الحالية.

## 10. الخطوات التالية بالترتيب

1. مراجعة وتثبيت خط الأساس ومتطلبات المنتج قبل أي تنفيذ.
2. تحويل مصفوفة قبول تثبيت APK إلى Test Corpus من ملفات سليمة وتالفة ومتنوعة الصيغ، مع احترام حقوق وخصوصية أصحاب الملفات.
