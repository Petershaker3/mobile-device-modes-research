# وثيقة خط الأساس ومتطلبات المنتج

> **هذه الوثيقة هي نقطة المرجع الوظيفية والمعمارية للمشروع.** ملفات المجالات ومراجعات الأدوات تحتفظ بالأدلة والتفاصيل. عند التعارض، لا نحذف التاريخ: نحدّث القرار هنا ونضع رابطاً إلى المراجعة التي تشرح سبب القرار.

**المستودع:** `Petershaker3/mobile-device-modes-research`  
**الحالة:** بحث وتحليل وتصميم متطلبات؛ لا يوجد تطبيق منتج منفذ أو تكاملات تم اعتمادها واختبارها على أجهزة فعلية حتى تاريخ هذه المراجعة.  
**آخر تجميع تنظيمي:** 12 نوفمبر 2026.

## 1. تعريف المنتج

منصة Windows متكاملة للتعامل مع أجهزة Android، تجمع الاتصال وقراءة البيانات وفهم أوضاع الجهاز وإدارة برمجياته وتطبيقاته وتشخيص مشكلاته من واجهة واحدة، مع إمكانية إتاحة الوظائف لوكلاء الذكاء الاصطناعي عبر MCP.

**بيئة التشغيل المعتمدة:**
- Windows 10 وWindows 11.
- Android 7.0 (API 24) فأحدث. هذا حد توافق مستهدف للبحث والتصميم، وليس ادعاء أن كل وظيفة أو بروتوكول متاح على كل إصدار أو جهاز.

**المحاور الوظيفية للمنتج:**
1. **اكتشاف الأجهزة والاتصال:** USB، ADB، Wireless ADB، Fastboot/Fastbootd، MTP/WPD، والواجهات الأخرى الموثقة ضمن النطاق.
2. **قراءة بيانات الجهاز:** الهوية والموديل والشركة والبناء وإصدار Android ومستوى التصحيح والأمان وABI والعتاد والخصائص المتاحة في كل وضع، مع توثيق مصدر كل معلومة وحدودها.
3. **الأوضاع والانتقالات:** اكتشاف وضع الاتصال الحالي، عرض قدراته، وتوثيق/تنفيذ الانتقالات المدعومة والمصرح بها، مع التحقق من النتيجة وعدم افتراض دعم موحد لكل الموديلات.
4. **قراءة معلومات السوفتوير:** معلومات النظام والبناء والإصدارات ومكونات البرمجيات والحزم المثبتة وحالة النظام وما يمكن قراءته بأمان من الجهاز أو ملفات السوفتوير. لا يعني ذلك أن التفليش أو الكتابة إلى أقسام الجهاز ضمن النطاق تلقائياً.
5. **إدارة التطبيقات والبرمجيات:** جرد التطبيقات، البحث والفلاتر والتفاصيل والتصدير والتثبيت والتحديث والتعطيل والإزالة والاستعادة وفق قيود Android.
6. **ملفات وأدوات التشخيص:** نقل/استعراض الملفات عبر القنوات المدعومة، Logcat والسجلات ومعلومات العمليات والتقارير وأدوات التشخيص التي تثبت فائدتها ومصدرها.
7. **إدارة الشبكة:** قراءة إعدادات الشبكة وPrivate DNS ومسارات حجب الإعلانات، مع إظهار حدود كل إصدار وصلاحية.
8. **دعم Windows:** تشخيص تعريفات USB وواجهات ADB/Fastboot/MTP وإصلاحها من مصادر رسمية موثوقة.
9. **الأتمتة والتكامل:** واجهة Desktop وطبقة خدمات موحدة وMCP محلي يمكّن Codex وغيره من وكلاء AI من تنفيذ المهام المسموح بها بصلاحيات وموافقات محكومة.

**حدود البحث الحالية:** قراءة أوضاع Qualcomm وMediaTek وبروتوكولاتها خارج النطاق، كما أن مقارنة التراخيص ليست ضمن البحث. لا نعتبر وجود وحدة قراءة أو وضع في قائمة المتطلبات دليلاً على دعمه لكل هاتف؛ الدعم يثبت لكل بروتوكول/وضع/موديل بالأدلة والاختبار.

## 3. ترتيب الأولويات الموحد

**الأولويات تُدار على مستوى محاور المنتج، وليست سلّماً يجعل تثبيت التطبيقات هو المنتج ثم يؤجل بقية وظائفه.** يجب أن تتقدم المنصة في مسارات متوازية مترابطة: الاتصال، قراءة البيانات، فهم الأوضاع، معلومات السوفتوير، إدارة التطبيقات، التشخيص، ثم التوسعات. لا يعني ذلك تنفيذ كل شيء دفعة واحدة؛ بل يمنع إسقاط أي محور رئيسي من تعريف المنتج.

### P0 — النواة المشتركة للمنصة

- دعم Windows 10 وWindows 11، والتحقق من متطلبات التشغيل والاعتماديات.
- اكتشاف أجهزة Android وتعدد الأجهزة وتحديد الجهاز صراحةً، مع USB وADB حيثما كان متاحاً.
- طبقة موحدة لاكتشاف واجهات الاتصال وحالة الجهاز والوضع الحالي، مع حالات خطأ موحدة.
- قراءة أساسية لمعلومات الجهاز والنظام والبناء وAndroid API وABI والخصائص المتاحة، مع مصدر ودرجة ثقة لكل حقل.
- جرد أساسي للتطبيقات والحزم المثبتة وبياناتها المتاحة، والبحث والتصفية.
- مسار تثبيت موثوق للصيغ الأساسية: APK وSplit APKs وAPKS.
- سجل عمليات وتدقيق وPreview/Approval للعمليات المؤثرة والتحقق بعد التنفيذ.
- تشخيص أولي لتعريفات Windows والتمييز بين مشكلة التعريف ومشكلة الكابل أو إعداد الهاتف أو التفويض.

### P1 — توسيع قدرات المحاور الأساسية

- Wireless ADB والاقتران والاتصال وإدارة الجلسات.
- توسيع قراءة البيانات حسب الوضع والموديل: معلومات النظام والبناء والحماية والعتاد والخصائص المتاحة.
- توسيع اكتشاف الأوضاع والانتقالات المدعومة، مع مصفوفة قدرات لكل موديل/واجهة وعدم افتراض التوافق العام.
- معلومات السوفتوير: جرد المكونات والحزم والإصدارات، قراءة بيانات ملفات السوفتوير وتحليل metadata والتوافق حيثما أمكن.
- إدارة التطبيقات بصورة أوسع: التحديث والإزالة والتعطيل والاستعادة والتصدير والفلاتر المتقدمة وسجل العمليات.
- APKM غير المشفر وXAPK/OBB عبر Adapters منفصلة بعد إثبات بنية العينات واختبارها.
- استعراض/نقل الملفات والسجلات وLogcat وأدوات التشخيص التي يثبت تدقيق المشاريع الجاهزة أنها تضيف قيمة.
- البحث والتنزيل من F-Droid وAPKPure وAPKMirror وفق تكامل مستقل لكل مصدر.
- تحسين تشخيص التعريفات وربط Hardware IDs بالواجهات والأوضاع.

### P2 — التوسعات المتقدمة

- DNS مخصص وحجب الإعلانات وإدارة إعدادات الشبكة وفق إصدار Android والصلاحيات.
- تقارير مقارنة الجهاز قبل/بعد، ومؤشرات صحة وتشخيص موسع.
- AAB والتحويلات الاختيارية، وتحليل ELF والاعتماديات الأصلية المتقدم.
- MCP/Codex بعد استقرار عقود Service Layer، مع أدوات قراءة وتغيير منفصلة وصلاحيات محكومة.
- أتمتة المهام وسير العمل متعدد الخطوات بعد ثبات الوظائف الأساسية.

### خارج النطاق أو مؤجل بقرار صريح

- قراءة أوضاع Qualcomm وMediaTek وبروتوكولاتها.
- الصيغ المشفرة أو مجهولة البنية إلى أن تتوفر عينات ودليل موثوق ومسار اختبار.
- التفليش والكتابة إلى أقسام الجهاز أو فتح/تجاوز الحماية ليست مستنتجة من عبارة «قراءة السوفتوير»؛ تحتاج قرار نطاق مستقل ومراجعة أمان وأدلة خاصة قبل إدراجها.

**ترتيب صيغ التطبيقات داخل محور التثبيت فقط:**

| الأولوية | الصيغة | المسار |
|---|---|---|
| P0 | APK | فحص ثم `adb install` |
| P0 | Base + Split APKs | تحقق المجموعة ثم `adb install-multiple` |
| P0 | APKS | Google bundletool وDeviceSpec |
| P1 | APKM غير المشفر | Parser/Adapter خاص بالبنية المكتشفة |
| P1 | XAPK | Parser/Adapter؛ وOBB مرحلة منفصلة |
| P2 | AAB | تحويل اختياري عبر bundletool؛ ليس APK جاهزاً |
| مؤجل | APKV المشفر وAPKM legacy المشفر | لا دعم قبل إثبات الحاجة ووجود عينات واختبارات مناسبة |

### مسارات وظيفية تفصيلية قائمة

- **إدارة التطبيقات:** قائمة التطبيقات System/User وEnabled/Disabled؛ بحث بالاسم وPackage ID؛ فلاتر تاريخ التثبيت والتحديث والمصدر وABI عند توفر البيانات؛ تفاصيل package/version/installer/UID/path؛ Install/Uninstall/Enable/Disable/Restore؛ تصدير APK أو Split APKs؛ وعمليات Batch بنتيجة مستقلة لكل تطبيق.
- **الاتصال وقراءة المعلومات:** اكتشاف USB interfaces وVID/PID وHardware IDs وCOM ports؛ ADB وFastboot وFastbootd وMTP/WPD؛ مسارات الشركات التي تقع ضمن النطاق؛ مصفوفة قدرات وانتقالات حسب الموديل؛ وكل حقل Read Info يحمل حالة Success / Unsupported / PermissionDenied / NotReported / Timeout / DeviceDisconnected / MalformedResponse.
- **DNS والشبكة:** التمييز بين Private DNS (DoT hostname) وDNS التقليدي وتطبيقات Local VPN؛ قراءة الحالة أولاً، ثم Preview وموافقة وتطبيق وتحقق.
- **تعريفات Windows:** قراءة PnP/SetupAPI/Configuration Manager وHardware IDs؛ اقتراح مصادر Microsoft/Google/OEM الرسمية؛ لا تثبيت أو إزالة تلقائية.
- **MCP/AI:** خادم محلي؛ Read-only افتراضياً؛ أدوات التغيير تفرض الموافقة داخل الخادم؛ لا Shell عام ولا Administrator مفتوح ولا اختيار تلقائي لأول جهاز.

## 4. المعمارية المنطقية الموحدة

```text
Windows Desktop UI                 AI Client (Codex)
        |                                  |
        |                           MCP Server (local)
        |                                  |
        +-----------> Application Services <+
                        |
     +------------------+-------------------------+
     |                  |                         |
 Device & Mode Services   Software & App Services   Windows Driver Services
     |                  |                         |
 USB / ADB / Fastboot   Package & Source Providers   Windows PnP APIs
 MTP / WPD / Mode Adapters  Software Inspection      Official Driver Sources
 Read Info / Diagnostics  Install / App Management   Repair / Verify
     |                  |                         |
     +------------------+-------------------------+
                        |
                 Shared Policy Layer
       Device Targeting / Capability Matrix / Approval / Audit / Reconciliation
                        |
                Android Device / Windows
```

**مبادئ الفصل:**
- Provider Adapter مسؤول عن اكتشاف التطبيق/الإصدار وحل رابط التنزيل؛ لا يثبت التطبيق.
- Format Adapter مسؤول عن تحليل صيغة الملف وإنتاج Install Plan؛ لا يقرر جهازاً من تلقاء نفسه.
- Device Adapter مسؤول عن الاتصال وتنفيذ عملية محددة على Serial معلوم.
- Application Service Layer تنسق المراحل وتفرض السياسات وتنتج نتيجة موحدة.
- GUI وMCP لا يتصلان مباشرة بأوامر shell أو تفاصيل parser.

## 5. مسار تثبيت التطبيق من البداية للنهاية

1. **Search:** البحث عن التطبيق في المصادر المحددة.
2. **Version & Variant Selection:** اختيار إصدار وvariant واضحين.
3. **Download Preview:** عرض المصدر والرابط النهائي والحجم والـhash المتوقع إن توفر.
4. **Download:** تنزيل متدرج إلى staging مع cancellation وإدارة partial files.
5. **Format Detection:** تحديد الصيغة من المحتوى والبنية، وليس الامتداد وحده.
6. **Package Inspection:** قراءة manifest والهوية والإصدار والحد الأدنى للنظام والتوقيع.
7. **Secure Extraction:** استخراج محدود وآمن عند الحاجة، بأسماء staging مولدة وحدود موارد.
8. **Device Matching:** مطابقة ABI/SDK/density/locale واختيار splits المطلوبة.
9. **Install Preview:** عرض الجهاز المستهدف والملفات والآثار والخيارات.
10. **Approval & Install:** موافقة مستقلة، ثم تنفيذ عبر install أو install-multiple أو bundletool.
11. **Verification:** إعادة قراءة package/version؛ وتبقى launch verification مرحلة اختيارية منفصلة.
12. **Reconciliation & Audit:** تسجيل النتيجة، إعادة قراءة حالة الجهاز والحزمة بعد timeout/disconnect، وتحديد ما إذا كانت العملية اكتملت أو فشلت أو بقيت حالتها غير محسومة؛ ثم تنظيف الملفات والجلسات المؤقتة بأمان. لا نفترض إمكانية Rollback لكل عملية، ولا نعرضها كقابلة للعكس إلا إذا كان ذلك مدعوماً ومختبراً للمسار المحدد.

لا يجوز القفز من Download إلى Install، ولا من ADB exit code إلى إعلان نجاح نهائي.

## 6. ضوابط الأمان المشتركة

- لا تثق في اسم الملف أو امتداده أو metadata التي يرسلها مصدر خارجي.
- HTTPS/TLS، redirects محدودة، ومنع SSRF والوصول إلى localhost/private network عبر روابط التنزيل.
- منع ZIP Slip وZip Bomb والروابط الرمزية وتضارب أسماء الملفات؛ حدود على عدد الملفات والحجم المضغوط والمفكوك والوقت والذاكرة والمساحة.
- Streaming للملفات الكبيرة، لا read-all إلى الذاكرة.
- تحقق APK signing certificate؛ hash يثبت تطابق bytes فقط ولا يثبت هوية الناشر.
- لا تعبر cookies أو tokens بين المصادر، ولا تسجل بيانات جلسات أو IMEI أو Serial دون ضرورة.
- لا downgrade أو test-only أو grant permissions تلقائياً.
- لا تنفيذ أوامر Shell عامة عبر MCP.
- لا إصلاح تعريفات أو تغيير DNS دون معاينة وموافقة وتحقق.

## 9. بيئة التشغيل المعتمدة وقرارات التنفيذ المتبقية

### 9.1 الأنظمة المستهدفة — محسومة

| المنصة | النطاق المعتمد | ملاحظة |
|---|---|---|
| Windows | Windows 10 وWindows 11 | يلزم تحديد Builds/editions ومعمارية x64/ARM64 في خطة الاختبار، ولا يغير ذلك نطاق الأنظمة المعتمد. |
| Android | Android 7.0 / API 24 فأحدث | الوظائف المتاحة تختلف حسب إصدار Android والموديل والشركة والصلاحيات؛ لا يعني الحد الأدنى أن كل ميزة تعمل على Android 7. |

### 9.2 قرارات تنفيذ لا تزال مفتوحة

| القرار | ما يجب تحديده | أثره |
|---|---|---|
| معمارية Windows | x64 فقط أولاً أم دعم ARM64 أيضاً | اختيار الحزم والاعتماديات وبناء CI |
| تغطية Android | مصفوفة إصدارات وموديلات فعلية للاختبار فوق API 24 | التحقق من اختلاف الأوامر والخصائص والأوضاع والصلاحيات |
| أدوات التشغيل | طريقة توفير ADB Platform Tools وJava/bundletool والمكونات الأخرى عند الحاجة | التثبيت والتحديث والتحقق من سلامة الاعتماديات |
| سياسة الإصدارات | تثبيت نسخ الأدوات ومواعيد تحديثها وآلية الرجوع | قابلية إعادة البناء وتجنب تغير السلوك دون مراجعة |
| حدود العمليات | مهلات كل عملية، وحدود الملفات والذاكرة والمساحة، وسلوك الإلغاء | حماية البرنامج من التعليق أو استهلاك الموارد |
| فشل العمليات الجزئية | حالات timeout/disconnect أثناء تثبيت splits أو نقل الملفات أو عمليات النظام | تصميم reconciliation وإعادة المحاولة ومنع الإبلاغ الكاذب عن النجاح |
| الاحتفاظ بالسجلات | مدة الاحتفاظ ومكان التخزين وحقول التنقيح | الخصوصية والتشخيص واستعادة سجل العملية |
| نطاق الكتابة للسوفتوير | ما إذا كانت هناك وظائف تعديل/تحديث/تفليش مستقبلاً، وما الأجهزة والعمليات المسموحة | لا تُبنى أو تُعرض عمليات كتابة/تفليش قبل قرار مستقل ومراجعة أمان واختبار خاص |

**قاعدة التعامل مع الفشل:** كل عملية طويلة أو متعددة الخطوات يجب أن تمتلك Operation ID وحالات صريحة مثل Pending وRunning وSucceeded وFailed وCancelled وOutcomeUnknown وNeedsReconciliation. لا تُعاد العملية تلقائياً إذا كان من الممكن أن تكون قد نُفذت جزئياً؛ افحص الحالة أولاً. يجب أن تكون عمليات التنظيف محدودة ومحمية من حذف ملفات لا تخص العملية الحالية.

## 10. الخطوات التالية بالترتيب

1. تم تدقيق الاتساق الأساسي بين الوثائق 00–12 وتحديث الفهرس وروابط المحاور؛ تبقى مراجعة تفصيلية متجددة عند تغير أي قرار أو مصدر.
2. تم التقاط Source HEAD SHAs للمرشحين الرئيسيين في [12](12-REUSE-AND-IMPLEMENTATION-PLAN.md)، وأعيدت مراجعة AdvancedSharpAdbClient وADB-Explorer وAdbGui في [13](13-source-revalidation-adb-file-core.md)؛ بقية المرشحين تحتاج مراجعة الفروق قبل الاقتباس. وتمت إعادة مراجعة المرشحين الأساسيين للتثبيت في [14](14-source-revalidation-app-installers.md).
3. تنفيذ Source Revalidation للمرشحين الأعلى أولوية، ثم إعداد corpus محلي غير حساس من outputs وملفات OTA/super/logcat/bugreport وAPK fixtures، دون جمع بيانات خاصة.
4. تنفيذ PoC مقارنة لـ.NET 10 وTauri/Rust في ADB USB/Wireless وmulti-device وcancellation وWindows PnP/WPD، ثم حسم Host/UI/ADB/MTP/MCP/dependency delivery.
5. تثبيت عقود DeviceHandle وCapability وOperation وResult وAudit، وخطة اختبار Windows 10/11 وAndroid API 24+ مع فصل Unit/Parser/Runtime/Hardware.
6. بعد موافقة تنفيذ مستقلة، تنفيذ النواة المشتركة ثم ربط المحاور عبر adapters قابلة للاستبدال، دون بناء برامج منفصلة لكل محور.
7. لا تبدأ أي كتابة على هاتف أو إصلاح تعريفات أو تغيير DNS أو تفليش/تحديث جهاز ضمن هذه المرحلة البحثية.

**لا نختار تقنية التنفيذ النهائية أو نبدأ إعادة كتابة النظام قبل مراجعة المرشحين الحاليين وتحديد ما يمكن اقتباسه مباشرة.** ولا تُعد هذه الوثيقة موافقة على تنفيذ أي تغييرات على هاتف أو Windows.
