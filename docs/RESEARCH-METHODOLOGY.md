# منهجية البحث وضبط جودة الأدلة

## 1. الغرض

توحيد طريقة جمع المعلومات ومقارنتها في هذا المستودع، ومنع تحويل ادعاءات الشركات أو وجود أوامر في الكود إلى حقائق توافق مؤكدة.

## 2. درجات الأدلة

| التصنيف | المعنى | ما يسمح باستنتاجه |
|---|---|---|
| **موثق رسمياً** | وثيقة من Android/AOSP أو Microsoft أو Google أو الشركة المصنّعة | يثبت ما تنص عليه الوثيقة ضمن نطاقها وشروطها |
| **موجود في الكود** | تنفيذ أو واجهة أو أمر موجود في مستودع الأداة | يثبت وجود التنفيذ، لا نجاحه على كل الأجهزة |
| **معلن من المطور** | صفحة رسمية أو سجل إصدار للأداة | يثبت أن المطور يعلن الميزة، لا أنها اختُبرت مستقلاً |
| **تجربة مجتمع** | تقرير مستخدم أو نقاش منتدى | قرينة محدودة مرتبطة بالجهاز والإصدار المذكورين |
| **مختبر فعلياً** | اختبار قابل لإعادة التنفيذ مع تسجيل البيئة والنتيجة | يثبت النتيجة ضمن بيئة الاختبار فقط |
| **غير متحقق** | لا يوجد دليل كافٍ أو لم يتم الفحص | يمنع عرض الميزة كحقيقة مؤكدة |
| **استنتاج/افتراض** | تحليل مبني على أدلة جزئية | يجب وسمه بوضوح وعدم تقديمه كحقيقة |

## 3. حالات التنفيذ والاختبار

استخدم الحالات التالية في جداول المقارنة:

- **Confirmed**: تم التحقق بالدليل المحدد، مع ذكر نطاقه.
- **Partial**: يعمل أو ثبت في جزء من النطاق فقط.
- **Claimed**: معلن من المطور ولم يُختبر مستقلاً.
- **Code evidence**: التنفيذ ظاهر في الكود ولم يُثبت سلوكه وقت التشغيل.
- **Needs audit**: يحتاج مراجعة كود/وثائق/إصدار.
- **Not verified**: لا يوجد إثبات كافٍ.
- **Unsupported**: ثبت أن المسار غير مدعوم ضمن الحالة المختبرة.
- **Not tested**: لم يُجر الاختبار بعد.

لا تستخدم كلمة «مدعوم» دون توضيح هل المقصود دعم معلن أم كود موجود أم اختبار فعلي.

## 4. بطاقة توثيق كل أداة

عند إضافة أو تحديث أداة، سجل قدر الإمكان:

1. الاسم والرابط الرسمي ومستودع المصدر.
2. تاريخ المراجعة ورقم الإصدار أو Commit SHA.
3. أنظمة Windows المدعومة ومتطلبات التشغيل.
4. أوضاع الاتصال والواجهات التي تتعامل معها.
5. الوظائف المعلنة مقابل الوظائف الموجودة في الكود.
6. الأدلة المستقلة وتجارب المجتمع، مع وصف الجهاز والإصدار إن توفرت.
7. القيود والمشكلات المعروفة.
8. حالة الاختبار الفعلي وبيئته ونتيجته.
9. مصدر كل ادعاء مهم.

## 5. نموذج تسجيل الاختبار الفعلي

| الحقل | القيمة المطلوبة |
|---|---|
| Test ID | معرف فريد |
| Date | تاريخ الاختبار |
| Windows | الإصدار والبنية والمعمارية |
| Device | الشركة والموديل |
| Android | الإصدار وAPI level |
| Connection | USB أو Wireless، ونوع الكابل/المنفذ عند الحاجة |
| Mode | MTP / ADB / Fastboot / غيره ضمن النطاق |
| Tool | الاسم والإصدار |
| Driver | الاسم والناشر والإصدار وHardware IDs |
| Steps | خطوات قابلة لإعادة التنفيذ |
| Expected | النتيجة المتوقعة |
| Actual | النتيجة الفعلية ورسالة الخطأ |
| Evidence | سجل/صورة/ملف ناتج بعد إزالة البيانات الحساسة |
| Verdict | Pass / Fail / Partial / Inconclusive |

## 6. قواعد السلامة والنطاق

- لا تنفذ تغييرات على هاتف حقيقي لمجرد أن البحث يقترحها؛ الاختبار العملي يحتاج موافقة مستقلة.
- لا تنفذ تثبيت أو إزالة تعريفات Windows أو تغيير DNS دون موافقة واضحة على الإجراء.
- استخدم المصادر الرسمية للتعريفات والبرامج، ولا تتجاوز التوقيع الرقمي أو حماية Windows.
- افصل دائماً بين USB enumeration، وربط تعريف Windows، وموافقة Android، ونجاح بروتوكول ADB/Fastboot/MTP.
- لا تعتبر نجاح أمر أو exit code دليلاً كافياً؛ أعد قراءة الحالة واختبر النتيجة.
- أخفِ IMEI وSerial وأي رموز اعتماد أو معرفات حساسة من السجلات المنشورة.
- لا تعمم نتيجة جهاز واحد على جميع أجهزة الشركة أو إصدارات Android.

## 7. حدود النطاق الحالية

- المستودع بحث وتوثيق ومقارنة، وليس برنامجاً منفذاً أو حزمة تعريفات.
- لا تُبحث تراخيص الأدوات في المقارنة الحالية.
- قراءة أوضاع Qualcomm وMediaTek خارج النطاق.
- لا تُدّعى اختبارات فعلية ما لم يوجد سجل اختبار مطابق للنموذج أعلاه.

## 8. صيانة الوثائق

- يبقى README.md ملخصاً وفهرساً، وتوضع التفاصيل في ملفات مستقلة تحت docs/.
- حدّث ملف المجال المعني فقط، وحدّث روابط الفهرس عند إضافة ملف.
- احتفظ بالمحتوى التاريخي المفيد، لكن انقل الاستنتاجات القديمة أو المتعارضة إلى حالة واضحة بدلاً من حذفها دون تفسير.
- راجع الروابط والإصدارات والتواريخ قبل وصف أي معلومة بأنها حديثة.
- لا تكرر نفس التفاصيل في أكثر من ملف؛ استخدم روابط داخلية إلى المصدر الأساسي.

## 9. سياسة إعادة استخدام المشاريع والمكونات

قبل اقتراح تنفيذ وظيفة جديدة، ابحث عن مشروع GitHub أو مكتبة أو أداة قائمة. سجل نتيجة البحث حتى إذا لم تجد مكوناً مناسباً، لتجنب إعادة البحث أو بناء شيء موجود دون مبرر.

عند وجود مرشح:
- حدد الوظيفة المطلوبة بدقة، ثم افصل بين ما يعلنه المشروع وما يظهر في الكود وما تم اختباره.
- سجل المستودع والإصدار وCommit SHA وتاريخ المراجعة والاعتماديات ونقاط التكامل.
- قيّم الصيانة، توافق Windows، الأمن، الأداء، جودة الأخطاء والسجلات، وتعدد الأجهزة.
- اختر بوضوح بين استخدام CLI/SDK، دمج مكتبة، Adapter، Fork محدود، تضمين جزء من المصدر، أو تنفيذ مستقل.
- لا تعتبر عدد النجوم أو وجود README أو نجاح CI دليلاً على ملاءمته لبرنامجنا.
- لا تنسخ مشروعاً كاملاً إذا كان المطلوب وظيفة يمكن استدعاؤها عبر واجهة مستقرة.
- لا تعتمد مكوّناً قبل مراجعة مصدره وتثبيت إصدار معروف واختبار تكامله.
- احتفظ بحدود استبدال واضحة واختبارات عقد حول كل Adapter.

## 10. سياسة MCP والذكاء الاصطناعي

عند تصميم تكامل الذكاء الاصطناعي، تعامل مع MCP كطبقة تكامل فوق خدمات البرنامج، لا كمصدر بديل لمنطق الأعمال أو الصلاحيات.

- تشارك GUI وMCP نفس Service Layer.
- ابدأ بـSTDIO محلياً؛ لا تفتح HTTP أو الشبكة افتراضياً دون حاجة ومراجعة أمنية.
- اجعل أدوات القراءة Read-only افتراضياً، وافصلها عن أدوات التغيير.
- استخدم Preview/Approval/Apply/Verify للعمليات المؤثرة في الهاتف أو Windows.
- لا تعرض Shell عاماً أو صلاحيات Administrator واسعة لوكيل الذكاء الاصطناعي.
- حدد الجهاز المستهدف صراحة عند وجود أكثر من جهاز.
- وثق مخططات الأدوات، الأخطاء، الصلاحيات، البيانات التي يمكن كشفها، وسياسة السجلات.
- اختبر الربط من Codex فعلياً؛ وجود خادم MCP أو نجاح الاتصال وحده لا يثبت أن المهام المطلوبة تعمل.
